Why SignalHub exists

Your hardest day should not depend on somebody else's control plane.

When a service fails, customers need a clear source of truth. SignalHub gives your team one place to detect impact, coordinate updates, notify subscribers, and preserve the evidence.

Customers remember the quality of your communication long after the incident is resolved.
01 / PUBLIC TRUST

Customer status pages

Publish service health, incidents, maintenance, metrics, history, and postmortems on your own domain.

02 / OPERATIONS

Incident response

Move from investigating to resolved with structured updates, ownership, impact, and durable delivery.

03 / DETECTION

Private monitoring

Run HTTP, TCP, DNS, SSL, ICMP, heartbeat, and private target checks from your network.

04 / GOVERNANCE

Audit evidence

Seal platform and tenant activity into hash chains, export it, and forward signed events to your SIEM.

01 · Plan the deployment

Start with the right operating boundary.

SignalHub can run on one controlled Docker host for a pilot or on Kubernetes for enterprise production. In both cases, treat the database, assets, keys, and notification providers as one recovery unit.

Required tools

  • Docker Engine with Compose v2, or Kubernetes 1.27 or newer with Helm 3.
  • MongoDB 8 configured as a replica set. SignalHub uses transactions.
  • Node.js 22 for local development and operator commands.
  • A DNS name, TLS termination, and a trusted reverse proxy or ingress.
  • Two independent high-entropy secrets for sessions and encrypted data.
  • SMTP for email delivery. S3-compatible storage for multiple replicas.

Clone and prepare

git clone https://github.com/rameshbgm/signalhub.git
cd signalhub
cp .env.example .env
openssl rand -base64 48
openssl rand -hex 32

Use the generated values independently. Do not reuse a session secret as an encryption key.

02 · Docker Compose

Run a pilot on one controlled host.

Compose starts MongoDB, the migration job, web replicas, and the durable worker. Keep the application port bound to loopback and publish it through a TLS reverse proxy.

Minimum production values

SESSION_SECRET=<independent-random-value>
ENCRYPTION_KEY=<independent-64-character-hex-value>
NEXT_PUBLIC_APP_URL=https://signalhub.at
ALLOW_PUBLIC_SIGNUP=false
ENABLE_DEV_QUICK_LOGIN=false
ALLOW_DEV_SEED=false
REQUIRE_WORKER=true

Start and bootstrap

docker compose config --quiet
docker compose up -d --build
docker compose ps

printf '%s' 'choose-a-unique-long-password' \
  | docker compose exec -T web \
      node dist-runtime/bootstrap.mjs --password-stdin

Validate

curl -fsS https://signalhub.at/api/health/live
curl -fsS https://signalhub.at/api/health/ready
docker compose exec web node dist-runtime/signalhubctl.mjs doctor
docker compose logs --tail=100 web worker migrate

03 · Kubernetes and Helm

Scale web and worker workloads independently.

Use an external MongoDB replica set, S3-compatible storage, and an externally managed Secret. The chart includes migration hooks, probes, disruption budgets, autoscaling options, topology spread, and NetworkPolicy.

Create the namespace and secret

kubectl create namespace signalhub
kubectl -n signalhub create secret generic signalhub-production \
  --from-literal=DATABASE_URL='mongodb://user:password@mongo-a,mongo-b,mongo-c/signalhub?replicaSet=rs0' \
  --from-literal=SESSION_SECRET='<session-secret>' \
  --from-literal=ENCRYPTION_KEY='<encryption-key>' \
  --from-literal=METRICS_TOKEN='<metrics-token>' \
  --from-literal=S3_BUCKET='signalhub-assets'

Core values

image:
  repository: ghcr.io/rameshbgm/signalhub
  tag: "1.0.0"

config:
  appUrl: https://signalhub.at
  assetStorageDriver: s3
  requireWorker: "true"
  trustProxyHeaders: "true"

secrets:
  existingSecret: signalhub-production

ingress:
  enabled: true
  className: nginx
  hosts:
    - host: signalhub.at
      paths:
        - path: /
          pathType: Prefix

Install and observe

helm lint deploy/helm/status -f values-production.yaml
helm upgrade --install signalhub deploy/helm/status \
  --namespace signalhub \
  --create-namespace \
  -f values-production.yaml

kubectl -n signalhub rollout status deployment/signalhub-signalhub-web
kubectl -n signalhub rollout status deployment/signalhub-signalhub-worker

04 · Identity and security

Connect enterprise identity without losing recovery.

SignalHub supports OIDC authorization code flow with PKCE, SAML assertions, SCIM 2.0 provisioning, TOTP MFA, recovery codes, fixed role mappings, and a local break-glass owner.

Identity sequence

  1. Create an OIDC or SAML connection in the platform console.
  2. Validate issuer, audience, callback URL, verified email, and optional MFA assurance claims.
  3. Create SCIM credentials and store the token once in the identity provider.
  4. Map identity-provider groups to fixed tenant or platform roles.
  5. Exercise joiner, mover, and leaver behavior before production.
  6. Keep one local MFA-protected platform owner for recovery.

Security baseline

01
Externalize every secretUse a secret manager, encryption keyring, signing keyring, and documented rotation procedure.
02
Bound administrative trafficUse TLS, trusted proxy hops, platform administrator CIDRs, and network policy.
03
Protect outbound monitoringPrivate targets are denied by default. Enable only with explicit egress policy.
04
Send evidence to your SIEMUse signed HTTPS delivery, retries, dead-letter alerts, and periodic export verification.

05 · Operations and recovery

Operate from signals, not assumptions.

Centralize JSON logs, Prometheus metrics, OTLP traces, health checks, worker heartbeats, queue depth, dead letters, authentication failures, migration drift, and SIEM delivery state.

Operator commands

npm run signalhubctl -- doctor
npm run signalhubctl -- preflight
npm run signalhubctl -- migrate --check
npm run signalhubctl -- audit --org <organization-id>
npm run signalhubctl -- backup --output signalhub.archive.gz
npm run signalhubctl -- restore --archive signalhub.archive.gz
npm run signalhubctl -- rotate-encryption-key

Recovery exercise

  1. Restore the MongoDB archive into an isolated environment.
  2. Restore or attach a point-in-time copy of assets.
  3. Run migrations with the target application release.
  4. Start one worker and one web process.
  5. Validate login, public pages, incident history, delivery, and audit chains.
  6. Record recovery time, gaps, owners, and follow-up work.
