## What changed from the idea list

- **A2 (AI-written messages for auto-incidents) is not a separate plan.** Its safety goal, never
  publishing raw check errors, is already fixed in commit `abca579` using `publicFailureMessage()`
  (no AI). An LLM rewrite would only see the same five error categories, so the marginal value is
  low. If wanted later, the draft builder from Plan 2 can be reused to polish the auto-incident
  body asynchronously. Not recommended now.
- **F2 guardrails are built into Plan 1** (redaction, untrusted-data wrapper, per-org opt-in,
  provider kill switch, usage log) instead of being a separate project.

## Decisions baked into the plans (change them before starting if you disagree)

1. **No vendor SDKs for LLM calls.** Plain HTTP through the existing `guardedFetch`, two wire
   formats: Anthropic Messages and OpenAI-compatible chat completions (covers OpenAI, Ollama,
   vLLM, LM Studio, LiteLLM, Azure/Bedrock behind a gateway). No new dependency in Plans 1-3.
2. **Configuration is platform-level plus per-organization opt-in.** Platform admin sets one
   provider for the installation (key encrypted like SMTP/SMS secrets); each organization Admin
   turns AI on for their organization. Per-organization keys are not built.
3. **AI drafts, a human publishes.** No feature in these plans publishes AI text by itself.
4. **Plan 4 uses the official MCP TypeScript SDK v2** (`@modelcontextprotocol/server`,
   Apache-2.0, depends on `zod ^4` which the repo already has). It is the only new dependency.
   Reason: the MCP spec's current revision (2026-07-28) changed the transport (no sessions,
   per-request metadata headers, header/body validation), so hand-rolling JSON-RPC is risky.
   The SDK line `@modelcontextprotocol/sdk@1.x` stops at revision 2025-11-25 and is not used.
5. **Statistics before LLMs** (anomaly detection, alert grouping) are out of scope here; they
   are Phase 3 in the idea list.

## Constraints that apply to every plan

- Read the relevant guide in `node_modules/next/dist/docs/` before touching a Next.js route
  or server-action convention (project `AGENTS.md`: this Next.js version has breaking changes).
  For Plan 4 read `node_modules/next/dist/docs/01-app/01-getting-started/15-route-handlers.md`.
- Schema change = new numbered migration in `db/migrations/` + matching `lib/postgres/schema.ts`
  update. Migrations are checksummed; never edit one that has been committed.
- Run `npm run verify` (lint with zero warnings, typecheck, tests, build) before the last commit
  of each plan. Commit finished tasks; do not leave them pending.
- Tests live in `tests/`, import with relative paths (`../lib/...`) like `tests/csv.test.ts`,
  and run with `npx vitest run tests/<file>.test.ts`.
- Database-backed code is not unit-testable here (integration tests need
  `INTEGRATION_DATABASE_URL` pointing at a disposable DB whose name contains "test"). Plans
  therefore keep logic in pure functions or in factories with injected dependencies, and
  list a manual check for the thin database wiring.
- Every AI call goes through `lib/ai` (Plan 1). No feature calls a provider directly.
- Never put secrets in prompts: monitor `authSecret`, `requestHeaders`, `requestBody`, SMTP/SMS
  keys, subscriber contact data. Build prompt context from an allowlist of fields.

## How to execute

Use `superpowers:subagent-driven-development` (one fresh agent per task plus review) or
`superpowers:executing-plans` (inline). Plans 1-3 touch shared files
(`app/admin/(protected)/incidents/actions.ts`, `lib/postgres/schema.ts`), so run them
sequentially, not in parallel.
